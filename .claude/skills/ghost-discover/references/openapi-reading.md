# Reading a FastAPI OpenAPI spec

Artifacts (under `.ghost/<api>/`): `spec.json` (current), `spec.prev.json` (previous run), `endpoints.json` (derived list).

## Where things are in `spec.json`
- `paths["/items/{item_id}"]["get"]` is one operation; method keys are lowercase.
- `operationId` is auto-generated by FastAPI (e.g. `read_item_items__item_id__get`) unless the author set it. It names `cases/<op_id>.json`.
- `parameters[]` entries have `in` = `path|query|header|cookie`, `required`, `schema`.
- `requestBody.content["application/json"].schema` is the body; it is often a `$ref` into `components.schemas`.
- `responses` keys are status codes as strings, plus possibly `default`.
- `security` / `components.securitySchemes` describe auth (apiKey, http bearer, oauth2).

## FastAPI specifics
- Statuses raised with `HTTPException` are NOT inferred; they appear only if the author declared `responses={...}`. So a spec with only 200 and 422 does not mean no 404/401/409 exist. That gap is what S2/S3 fill.
- A `422` entry (`HTTPValidationError`) is added automatically only in some conditions (routes with params/body and no own 422/4XX/default). A missing 422 does not prove the route cannot return one.
- Empty response schema (`{}`) means no `response_model`; response shape is unchecked.

## Checks worth noting at discovery
- Operations lacking `operationId` or with duplicate ids.
- Required params with no `example`/`default` (cases will need generated values).
- Endpoints with write methods (POST/PUT/PATCH/DELETE): these are gated by `allow_writes`.
- Compare `spec.json` to `spec.prev.json` only for a headline count; classification belongs to `contract-keeper` (see ghost-contract drift rules).
